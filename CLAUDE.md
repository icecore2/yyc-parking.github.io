# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Five independent apps share one domain model: Calgary parking zones from six providers (`parkplus_on_street`, `cpa_off_street`, `calgary_transit`, `impark`, `indigo`, `precise_parklink`), their rate schedules, and street/lot geometry.

| Path | What it is |
|------|------------|
| `webapp/` | **Main product.** Next.js 16 (App Router) + React 19 + Tailwind v4 + shadcn/ui (new-york) + MapLibre GL + Firebase (Auth, Firestore, App Check) + Stripe. |
| `services/parking-sync/` | Node TS service. It fetches the provider endpoints, stages them in local SQLite, diffs by hash, and pushes changes to the Firestore `parking_data` collection. It runs every 30 minutes in `.github/workflows/parking-sync.yml`. |
| `index.html`, `js/`, `css/`, `server.js` | Legacy static Leaflet app, deployed to GitHub Pages from the repo root on every push to `main`. |
| `android/` | Kotlin + Jetpack Compose + osmdroid app. |
| `ios/` | SwiftUI + MapKit app. Core logic is also exposed as a Swift package for `swift test`. |
| `data/commercial_parking.json` | Curated commercial-lot dataset. Copies live in `android/.../assets`, `android/.../resources` and `ios/.../Resources`, so keep them in sync when you edit it. |

The rate parser, Web Mercator→WGS84 conversion and provider registry are implemented separately in each platform: `webapp/lib/parking/`, `js/`, `services/parking-sync/src/utils/`, `android/.../service/` and `ios/.../Services/`. A behaviour change to one usually needs the same change in the others.

## Commands

From the repo root (these proxy into the subprojects):

```bash
npm run webapp:dev        # Next dev server on :3000 (/, /app, /pricing, /account, /expenses)
npm run webapp:build
npm run webapp:test       # webapp test suite
npm run sync:run          # one-time provider sync
npm run sync:daemon -- --interval=30
npm run sync:test
npm start                 # legacy Leaflet app on :8080
npm test                  # legacy app tests (test/*.js)
```

Inside `webapp/`: `npm run lint` (ESLint 9 flat config, `eslint-config-next`). There is no `typecheck` script, so run `npx tsc --noEmit` to typecheck.

Native: `cd android && ./gradlew testDebugUnitTest assembleDebug`; `cd ios && swift test`.

**Tests are plain Node scripts that use `assert`, with no test framework.** To run a single suite, run its file directly, e.g. `node webapp/test/test_pin_geometry.js`. A suite stops at its first failed assertion. The `sync` service runs `.ts` through `node --experimental-strip-types`, so it needs Node 22 or later. Its imports must use explicit `.ts` extensions.

## Webapp architecture

### Next.js version
`webapp/AGENTS.md` (re-generated by `next dev`) warns that this Next.js version has breaking changes from older releases. Read the relevant guide in `webapp/node_modules/next/dist/docs/` before writing Next-specific code, and follow any deprecation notices.

### Parking data pipeline (fallback chain)
`lib/parking/data-service.ts::fetchCalgaryParkingZones` is the single client entry point:
1. It checks the `sessionStorage` cache (`CACHE_KEY = 'yyc_parking_zones_v3'`; bump the version when the zone shape changes).
2. It calls `GET /api/parking` (`app/api/parking/route.ts`). The route reads the Firestore `parking_data` collection. If that is empty or fails, it reads `../services/parking-sync/data/local_parking.db` through `node:sqlite`, loaded with `eval('require')` on purpose. If both fail, it returns `{source:'empty'}`.
3. If there is still no data, it calls the City of Calgary ArcGIS FeatureServer directly (`ARCGIS_URL`), converts Web Mercator to lng/lat, and appends the curated off-street and transit zones from `SAMPLE_CALGARY_ZONES`.
4. As a last resort it returns `SAMPLE_CALGARY_ZONES` as-is.

Coordinates are always `[lng, lat]`. A zone pin sits at the midpoint of the zone's primary polyline (`geometry.ts::getPrimaryPath` + `pointAlongPolyline(path, 0.5)`), not at the stored centroid. Both the API route and the client follow this rule, and `test_pin_geometry.js` enforces it.

### Map
`app/app/page.tsx` is a large client component that owns all map state. It loads `components/map/MapLibreView.tsx` with `next/dynamic` and `ssr:false`. MapLibre and the landing-page `MiniMapTeaser` set `config.WORKER_URL = '/maplibre-gl-worker.mjs'`, served from `public/`. Keep the worker files in `public/` in step with the installed `maplibre-gl` version.

### Z-index contract (enforced by `test/test_ui_layering.js`)
- The map container is an isolated stacking context at `z-index: 0`. Pins and popups inside it must stay at or below 30.
- shadcn primitives in `components/ui/` use these fixed layers: Sheet overlay/content `z-[1000]`/`z-[1010]`; Dialog `z-[1100]`/`z-[1110]`; Select, Dropdown and Tooltip content `z-[1200]`.
The tests read the source text of these components and of `globals.css`. If you change those classes or selectors, update the test too.

### Auth, tiers and persistence
- `lib/firebase/client.ts` initializes the Firebase client with placeholder defaults, so the app still builds and runs without env vars. In that "simulated local mode" `auth`/`db` may be empty objects.
- `lib/firebase/auth-context.tsx` provides `useAuth()` → `{ user, tier, isPro, ... }`. Tiers are `free` | `pro` | `admin`. If Firebase isn't configured, sign-in creates demo users whose uid starts with `demo_`.
- `lib/firebase/firestore.ts` is a dual-backend data layer. Real users read and write `users/{uid}/{favorites|sessions|vehicles|locations|preferences}`. `demo_*` users fall back to `localStorage` keys scoped by uid. After a mutation it fires `USER_DATA_CHANGED_EVENT` so other views can refresh. Payloads are passed through `sanitizeFirestorePayload` to strip `undefined` values.
- `webapp/firestore.rules` validates every field and makes `tier`/`role` immutable from the client. Only the Admin SDK (Stripe webhook) may raise a user's tier. If you add a stored field, update both the rules and the documented data model at the top of the rules file. `test_example_data_and_onboarding.js` checks the rules file.
- Pro-only features (Cheapest Spot Finder, tow alarms, cloud favorites) are gated with `ProGateModal`.

### Example data / onboarding
`lib/parking/example-data.ts` seeds sample vehicles, sessions, locations and favorites marked `isExample: true`, grouped by `EXAMPLE_IDS_BY_SECTION`. The account, expenses and map pages show them until the user dismisses them. Dismissal state is stored at `users/{uid}/preferences/onboarding`. `components/onboarding/` holds the walkthrough. The onboarding test checks that every consuming page honours the `isExample` flag.

### API routes and App Check
- `POST /api/stripe/checkout` calls `verifyAppCheckRequest` first (`lib/firebase/verify-app-check.ts`). Clients must call it through `fetchWithAppCheck` (`lib/firebase/app-check-fetch.ts`), which adds the `X-Firebase-AppCheck` header. If the Admin SDK isn't configured, verification is skipped in development and returns 503 in production. Admin credentials come from the `FIREBASE_ADMIN_*` env vars, or from ADC on Cloud Run/App Hosting (`lib/firebase/admin.ts`).
- If `STRIPE_SECRET_KEY` is missing or starts with `sk_test_demo`, Stripe checkout and the webhook run in demo mode (a simulated success redirect or a skipped webhook).

### Config and deploy
- Env vars are listed in `webapp/.env.example`. `NEXT_PUBLIC_*` values are inlined at build time, so the Dockerfile and `apphosting.yaml` must pass them with `BUILD` availability.
- Deploy targets: Firebase App Hosting (`webapp/apphosting.yaml`, backend `calgary-parking-map`, `next.config.ts` `output: "standalone"`) and Docker (`webapp/Dockerfile`, `docker-compose.yml` on `127.0.0.1:3005`). `firebase.json` also points Hosting at `webapp/out` and deploys `webapp/firestore.rules`.
- The import alias `@/*` maps to `webapp/*`.

## Sync service architecture
`src/index.ts` (`ParkingSyncCoordinator`) runs each fetcher in `src/fetchers/` (all extend `base.ts`) and normalizes the results to `NormalizedParkingRecord` (`types.ts`). It upserts them into SQLite (`db/local-db.ts`, written to `data/local_parking.db`, the file the webapp API also reads), hashes each record (`utils/hasher.ts`), and diffs against the remote (`sync/diff-engine.ts`). Changed records go to `sync/pusher.ts`, which writes through a `RemoteDatabaseAdapter` (`remote/firestore-adapter.ts` or `mock-adapter.ts` for tests). If you change the remote document shape, update the reader in `webapp/app/api/parking/route.ts` and `mapProviderNameToId` to match.
